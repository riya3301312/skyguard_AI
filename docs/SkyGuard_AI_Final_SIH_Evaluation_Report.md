# SkyGuard AI - Final SIH Evaluation Report

_Generated by `scripts/make_report.py` from `artifacts/` on 2026-09-29T00:17:16+00:00. All numbers come from the evaluation scripts._

## 1. Executive summary

SkyGuard AI is a production-quality SIH **prototype** observation-quality layer for Automatic Weather Stations (temperature, pressure, relative humidity). On the **frozen final test** (94,382 hourly observations, 22 Indian stations including 4 held-out stations, unseen seed 9001, unseen injection profile) the selected SkyGuard Hybrid achieved precision 0.803, recall 0.483, F1 0.603, PR-AUC 0.670, ROC-AUC 0.891 with 0.221 false alerts per station-day; event-level recall 91.8%. Real-time processing p95 latency was 861.4 ms per observation on the host PC.

Limits of these claims are listed in section 16. This is not mission-critical production infrastructure.

## 2. Indian use case

Remote and data-sparse Indian AWS sites report over intermittent mobile links, run on solar/battery power and span very different climates. SkyGuard therefore combines station-specific baselines, T/P/RH physical consistency, neighbour (spatial) evidence when it exists, explicit weather-event reasoning, store-and-forward uplink handling and a tiny edge-check library for ESP32-class loggers.

## 3. Architecture

```text
AWS / edge logger (C checks) -> store-and-forward uplink -> FastAPI ingestion (typed, validated, idempotent)
-> deterministic QC (config) -> temporal features -> multivariate (T/P/RH) features -> spatial features (if neighbours)
-> gradient-boosted detector -> isotonic calibration (autoencoder + regional-suppression rule evaluated, not selected)
-> fault-pattern + parameter classifiers -> severity -> explanation -> sensor health -> correction recommendation
-> maintenance risk -> SQLite (raw immutable) -> SSE live stream -> React dashboard
```

## 4. Dataset provenance

* Source: Iowa Environmental Mesonet (IEM) ASOS/METAR archive, network IN__ASOS. Original producer: India Meteorological Department (IMD) aerodrome meteorological offices (METAR/SPECI reports exchanged via WMO GTS).
* API: https://mesonet.agron.iastate.edu/cgi-bin/request/asos.py
* These are aerodrome surface observations, not the IMD AWS network feed. They are used as a real Indian AWS-like observation stream.
* 22 stations kept (hourly grid, completeness >= threshold); 12 excluded (completeness below threshold, recorded in `data/processed/stations.json`).
* Raw files are stored gzip-compressed exactly as received with SHA-256 in `data/raw/iem_metar/PROVENANCE.json` and are never modified.
* Pressure is the METAR altimeter setting (QNH, sea-level reduced); temperature resolution is 1 °C.
* ESSDP/INCOIS Mahabaleshwar and GMX600 metadata point to IITM distribution (no open bulk download); NCAOR's portal had a TLS certificate error; Meghalaya's API requires a key; IMD DSP requires registration. These were therefore not used.

## 5. Anomaly injection method

Injected values are quantised to the source resolution so no precision shortcut exists. Regional weather events are injected as labelled NON-anomalies. ## 6. Models

Baselines: fixed thresholds; rolling robust z-score; Isolation Forest; MLP temporal autoencoder (12-hour windows). Calibration: isotonic regression on validation.

## 14. Development integrity notes (disclosed)

* The final benchmark was frozen before any training; `run_log.jsonl` records every final-evaluation run.
* A bug in the regional-event rule (a shared humidity deviation could suppress an isolated temperature spike) was found by an integration test on synthetic stations and fixed; the model was retrained. The final test had not been evaluated at that point.
* The operating-point policy was changed from 'max validation F1' to 'max validation F1 subject to <= 0.2 false alerts per station-day' after false alerts were observed while replaying the SIH demo, whose clean data come from the test period. Thresholds are still computed only on validation and the change is required by the specification's emphasis on low false alarms; the frozen final evaluation was run once, afterwards.
* After the policy change, validation selected the temporal+multivariate+spatial variant over the full variant (validation F1 tie within 0.001); the autoencoder and regional-suppression rule are therefore not in the deployed model but are reported in the ablation.

## 16. Limitations

* Data are IMD aerodrome METAR observations (hourly, 1 °C resolution, QNH pressure), not the IMD AWS network feed.
* Evaluation uses injected faults on real data; real undetected faults in the source are labelled normal.
* Drift/step onsets are labelled from their first row, which caps row-level recall; event-level recall is reported too.
* Spatial evidence exists only where neighbours are within the configured radius (dense in the south-Indian cluster); a drifting neighbour can bias the neighbour median and cause low-severity alerts at healthy neighbours.
* 41.3% of injected regional weather events still produced at least one alert row with the selected variant (see ablation).
* SIH scenario A (clean station) failed in the demo replay: one false DRIFT alert in 124 clean observations.
* Live single-observation latency is several hundred ms on this PC (pandas feature recomputation + neighbour revisions); adequate for hourly AWS data but not optimised.
* Edge: no ESP32 hardware was available; sizes come from a cross-compiled object, runtime from the host; no energy numbers.
* Single-process prototype (SQLite, one engine lock); PostgreSQL and horizontal scaling are the documented scale path.
* Sensor-health and maintenance risk are data-quality indicators, not physical hardware diagnostics or failure predictions.
