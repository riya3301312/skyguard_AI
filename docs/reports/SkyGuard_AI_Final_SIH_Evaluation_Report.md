# SkyGuard AI - Final SIH Evaluation Report

_Generated by `scripts/make_report.py` from `artifacts/` (final evaluation run 2026-09-29T07:12:36+00:00). Every number is read from the evaluation artifacts._

## 1. Executive summary

SkyGuard AI is a **production-oriented SIH prototype**: an observation-quality layer for Automatic Weather Station temperature, pressure and relative humidity. It is not production infrastructure (see Limitations).

On the **v2 frozen final benchmark** (94,367 hourly observations; 22 Indian stations including 4 held-out stations; unseen seed 9002; unseen injection profile; frozen 2026-09-29T06:16:12+00:00 before this hardening pass) the selected SkyGuard Hybrid achieved:

* precision 0.820, row-level recall 0.457, F1 0.587, PR-AUC 0.688, ROC-AUC 0.903;
* 0.184 false alerts per station-day; event-level recall 90.1%;
* regional weather events with any alert: **13.4%** (same model without the weather-vs-sensor decision rules on the same data: 43.3%);
* held-out stations F1 0.577 vs seen stations 0.589;
* SIH scenarios: 11/11 passed; Docker: **ENVIRONMENT-UNVERIFIED** - No Docker engine is installed on the verification machine; build/startup/health/smoke were NOT run.

## 2. Dataset provenance

* Observations come from the **Iowa Environmental Mesonet (IEM) archive** (https://mesonet.agron.iastate.edu/cgi-bin/request/asos.py), network IN__ASOS.
* They originate from **Indian aerodrome METAR/SPECI reports** (India Meteorological Department (IMD) aerodrome meteorological offices (METAR/SPECI reports exchanged via WMO GTS)).
* This is **not the IMD AWS network feed**. It is used as an Indian AWS-like observation stream / proxy benchmark; results must not be read as performance on the IMD AWS network. Real AWS data, if obtained, would be a separately documented dataset with its own provenance and evaluation.
* 22 stations kept on an hourly grid; 12 excluded for completeness (recorded in `data/processed/stations.json`). Raw files are stored exactly as received with SHA-256 in `data/raw/iem_metar/PROVENANCE.json` and are never modified.
* Temperature resolution is 1 °C; pressure is the METAR altimeter setting (QNH).

## 4. Models and decision layer

Baselines: fixed thresholds; rolling robust z-score; Isolation Forest; MLP temporal autoencoder. Final: SkyGuard Hybrid, variant `full` (gradient-boosted detector + isotonic calibration + fault-pattern and parameter classifiers), alert threshold 0.23, followed by the validated weather-vs-sensor decision layer `{"confirm_persistent": true, "k6": 1.5, "c3": 0.5, "max_shared": 0.5, "regional_suppress": true, "regional_min": 0.5}`: persistence-aware DRIFT/STEP confirmation and regional-evidence suppression that never suppresses a station exception or a deterministic-QC fault.

## 12. Regression fixes

### Clean-station false DRIFT alert (SIH scenario A)

* Root cause: At the remote station VOPB (2024-08-05 10:00, demo replay) humidity swung from about 7.6 % below to 4.1 % above its time-of-day baseline within a few hours (weather). No feature was extreme (RH robust z 1.0) but the detector scored a single hour 0.63 and the pattern classifier called it DRIFT; nothing required a drift to be sustained. Window dump: artifacts/regression/clean_station_false_drift_window.csv.
* Implementation change: Persistence/trajectory-aware confirmation: DRIFT/STEP_OFFSET is alerted only if the attributed parameter's 6-h mean deviation exceeds k6 robust scales, the deviation stays one-signed over the 4-h persistence window (>= c3 scales), DRIFT is one-signed over 24 h, and the deviation is not shared by neighbours. k6/c3 chosen on validation.
* Regression test: test_clean_station_no_false_drift, test_clean_station_no_false_drift_on_demo_window, test_transient_change_not_classified_as_drift, test_persistent_drift_detected, test_persistent_step_detected, test_step_followed_by_recovery_not_confirmed
* Validation result: validation DRIFT+STEP false-positive rows 467 -> 321
* Final-test impact: v2 paired: FA/station-day 0.464 -> 0.184, event recall 95.0% -> 90.1%, row recall 0.592 -> 0.457; scenario A PASS

### Regional weather events raising sensor-fault alerts

* Root cause: Most validation false alerts during injected regional events were DRIFT/STEP calls on short, cluster-wide changes, concentrated at stations with a single neighbour and at event onsets where stations are one interval out of phase.
* Implementation change: Regional evidence score with +/-1 interval alignment and coverage weighting; station-exception detection; validated rule that does not raise a sensor-fault alert for regional evidence without a station exception; persistence confirmation also rejects deviations shared by neighbours.
* Regression test: test_regional_weather_not_sensor_fault, test_regional_weather_with_isolated_station_exception, test_step_during_regional_weather_is_not_a_station_step, test_alert_explanation_contains_regional_evidence
* Validation result: regional-event instances with any alert 23.1% -> 5.6%
* Final-test impact: v2 paired: regional events alerted 43.3% -> 13.4%

### A drifting neighbour biasing the neighbour median

* Root cause: The first-pass demo showed low-severity alerts at healthy stations next to a station with a pressure drift: the neighbour median assumed neighbours were clean.
* Implementation change: Robust neighbourhood: with >= 3 neighbours, a neighbour further than 3 robust spreads from the others is excluded before the median/MAD (feature version fv2).
* Regression test: test_bad_neighbor_does_not_dominate, test_neighbor_missing_does_not_crash
* Validation result: covered by retraining on fv2 features (selection.json)
* Final-test impact: included in all v2 numbers

### First-pass fixes carried forward

* Root cause: regional rule could suppress an isolated spike when another variable was shared; first station to report an hour had no neighbour context in live streaming; all-NaN spatial columns crashed training on sparse networks; truth file listed as replay scenario; e2e server blocked on an unread stdout pipe
* Implementation change: every strongly deviating variable must be shared; provisional -> revised spatial scoring; drop never-observed features; scenario filter; server log to file
* Regression test: test_spike_detection_explanation_and_raw_preservation, test_stream_engine_matches_batch_pipeline, test_training_is_reproducible_with_fixed_seed, test_metrics_and_replay_validation, tests/e2e
* Validation result: n/a (correctness fixes)
* Final-test impact: included

## 14. Limitations

* Proxy data: Indian aerodrome METAR via IEM, not the IMD AWS network feed; 1 °C temperature resolution; QNH pressure.
* Evaluation uses injected faults on real observations; undetected real faults in the source are labelled normal.
* Row-level recall (0.457) is much lower than event-level recall (90.1%): drift/step alerts are raised only once the deviation is sustained, and early low-magnitude drift rows are not flagged.
* 13.4% of injected regional weather events still raised at least one alert.
* Spatial evidence needs neighbours within the configured radius; isolated stations rely on temporal + multivariate evidence.
* ESP32-compatible C edge library validated by cross-compilation and host execution. Physical ESP32 hardware validation and energy measurements were not performed.
* Docker: **ENVIRONMENT-UNVERIFIED** - No Docker engine is installed on the verification machine; build/startup/health/smoke were NOT run.
* SQLite single-process prototype (one engine lock); live single-observation latency is a few hundred ms on this PC.
* Sensor health and maintenance risk are data-quality indicators, not hardware diagnostics or failure predictions.
